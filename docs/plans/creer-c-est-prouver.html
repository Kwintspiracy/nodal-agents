Ce que la vérification a corrigé dans ce plan

Le point 3 disait « sous un projet déclaré ⇒ code ». Seul, c'était faux. Le registre se remplit tout seul à partir des fichiers de code qui portent un manifeste : ne regarder que la déclaration aurait typé « document » le premier package.json d'un dépôt neuf, et plus rien ne l'aurait jamais déclaré. La règle : racine à manifeste ou projet déclaré de code ⇒ code ; sinon document. Un projet déclaré de documents ne fait pas de ses fichiers du code.

« Un HTML se referme », et le parseur HTML5 ne le dit pas. La norme referme d'elle-même un <div> resté ouvert à </body>. Le constat lit donc les balises une à une et tient la pile de celles dont la fermeture est obligatoire.

« Un CSS s'analyse » ne se vérifie pas avec un parseur CSS. Sondé : css-tree acceptait un bloc jamais refermé et refusait l'imbrication moderne. Le constat est devenu structurel (accolades, parenthèses, chaînes et commentaires se referment), et le premier test était vert pour la mauvaise raison.

« Un markdown a un titre » acceptait deux faux titres, trouvés en sondant : un en-tête YAML, et une liste suivie d'un filet.

Ce que tu verras changer

Trois fichiers écrits ne se ressemblent plus. Aujourd'hui la carte affiche le chemin absolu, coupé à droite : trois écritures montrent trois fois le même préfixe et jamais le nom du fichier. Tu as cru voir « trois diffs sur le même fichier ». C'étaient SKILL.md, base.css et base.html — exactement les trois fichiers que tu avais demandés.

La consigne passée au travail devient lisible. La ligne « Handed to the work » est tronquée à une ligne. Elle porte 1 649 caractères, et c'est là qu'on voit qu'Alfred a inventé des exigences que personne ne lui avait données. Tu le lui as reproché ; l'écran te cachait la preuve.

Un skill cesse d'être un projet de code. L'outil d'écriture étiquette tout ce qu'il écrit « projet de code ». Nodal cherche alors les commandes de test du dossier, n'en trouve pas, et affiche « non configuré » sur un travail qui n'avait aucun test à lancer.

Et un document se vérifie, sans réglage. C'est ta règle : une vérification a lieu dès qu'il y a création de quelque chose. Pour un document, cela ne veut pas dire lancer des tests — cela veut dire constater qu'il existe, qu'il se lit, qu'il n'est pas vide, et qu'il est bien formé selon son type. Rien de tout cela n'exécute quoi que ce soit : aucune approbation, aucun écran, aucune configuration.

Ce que ça ne contient pas

  • Le coût d'un tour de chat — 18 500 jetons pour dire bonjour, quatre chantiers mesurés hier. C'est la PR d'après. Les mélanger referait une PR fleuve.
  • Les commandes de projet découvertes et approuvées dans le canal (v7-C) et les critères tirés de la demande (v7-D) — ils supposent le typage de cette PR.
  • Le vérificateur d'envoi (« le message est-il arrivé ») — il lit la file d'envoi, pas un fichier : autre chemin, autre lot.
  • « New conversation » sur la page Files — c'est ton arbitrage, pas un chantier. Je ne le retire que si tu le dis.

Les cinq points

1 Le nom du fichier se lit S

Le nom de base passe en tête ; le dossier suit, en gris, tronqué par la gauche — c'est la fin d'un chemin qui porte le sens. Le chemin complet reste au survol.

Preuve — trois fichiers d'un même dossier : les trois noms se distinguent, aucun ne contient le préfixe commun.

2 La consigne passée au travail se déplie S

Une ligne repliée, la consigne entière dépliée, dans le style des notes. Pas de composant neuf : celui des blocs dépliables existe.

Preuve — une consigne de 1 649 caractères se lit en entier une fois dépliée ; repliée, elle tient sur une ligne.

3 Un fichier créé est typé pour ce qu'il est M

La règle est mécanique, zéro LLM : le fichier est-il sous une racine à manifeste, ou sous un projet déclaré de code ? Alors « projet de code », comme aujourd'hui. Sinon « document ». Le type « document » a désormais sa règle de nommage — le fichier lui-même, la même que celle d'un classeur — et la carte du fichier porte sa clé pour que l'écran retrouve son état.

Preuve — un fichier écrit dans un projet déclaré reste « projet de code » ; le même fichier écrit dans le dossier partagé devient « document » ; aucun des deux ne lève.

4 Un document se vérifie tout seul M

Un vérificateur sans pouvoir : il ouvre le fichier, rien de plus, et constate.

Constat Vrai pour
le fichier existe là où c'est annoncé tous
il n'est pas vide tous
il se décode tous
il est bien formé un markdown a un titre · un CSS et un HTML se referment · un JSON et un SVG se parsent

Une extension inconnue s'arrête aux trois premiers constats — et le dit, plutôt que d'inventer une règle. Le résultat s'écrit là où toutes les preuves s'écrivent : le récapitulatif de livraison et la barre d'état n'ont rien à apprendre.

Preuve — un markdown sans titre est rouge et dit pourquoi ; un CSS dont un bloc ne se referme pas est rouge, avec la ligne ; les trois fichiers du skill sont verts ; un fichier supprimé entre l'écriture et la vérification est rouge, pas absent. 17 tests sur le vérificateur, 2 de bout en bout par la vraie finalisation.

5 La page Approvals en anglais XS

« Approuver une fois », « Toujours pour cet outil » dans un tableau de bord anglais. Fait : boutons, toasts et dialogues de confirmation.

Sa place dans la file

Cette PR passe après les deux de « Parler, c'est se souvenir » : un agent qui republie une annonce dans un Discord public, et qui répond aux accusés de réception de ses propres messages, coûte plus cher qu'un nom de fichier tronqué.

L'ordre interne

1 et 2 d'abord : ce sont des heures, et ils rendent lisible le fil sur lequel on va juger le reste. Puis 5, qui est une minute. Puis 3 et 4 ensemble : le 3 seul rendrait un skill non vérifiable au lieu de mal vérifié.

Ce que cette PR ne prétend pas régler

  • Un agent peut toujours écrire « vérifié » dans sa prose sans que rien ne l'ait prouvé. Le mot lui appartient ; l'écran dira juste, à côté, ce que Nodal a réellement constaté.
  • Un agent en runtime CLI n'écrit pas ses appels au modèle là où le fil les lit : son fil ne peut compter ni jetons ni coût. La barre dit « no usage recorded » plutôt qu'un faux zéro.
  • La création d'un agent n'est pas une transaction, et supprimer le ROOT n'a pas de règle de succession. Les deux sont au backlog du harnais.
