Vérifier & Corriger

Aujourd'hui, quand un agent finit une tâche, c'est lui qui déclare « c'est fait » — et personne ne vérifie. Demain, Nodal vérifie lui-même tout ce qui peut l'être, fait relire le reste par les relecteurs que tu as choisis, et ne laisse plus un agent dire « fini » si ce n'est pas vrai.

Le problème vécu

Aujourd'hui

L'agent finit son travail et écrit :

« C'est fait ! J'ai lancé les tests, tout passe. Le fichier est envoyé. ✓ »

Rien ne prouve qu'il les a lancés, ni que le fichier est parti. Parfois c'est vrai. Parfois tu découvres le lendemain que l'app ne démarre plus, ou que le message n'est jamais arrivé.

Demain

Nodal vérifie lui-même, après le travail :

Preuve : pnpm typecheck vert (8 s) → pnpm test → 214 tests verts. Message relu dans le canal : présent. Relu par 2 relecteurs : aucun bloquant. Succès vérifié.

Le mot « vérifié » veut enfin dire quelque chose : la machine l'a constaté, pas l'agent.

Toutes les tâches ne sont pas du code

Une tâche, c'est un job qui produit quelque chose — du code, un fichier, un message envoyé, un document livré. Un tour de chat n'en est pas une : une réponse conversationnelle n'est ni prouvée ni relue, et l'UI ne lui affiche aucun état de vérification.

Trois familles de livrables, trois façons de prouver — et chaque run te dit laquelle s'applique.

Prouvable

La machine tranche

Le livrable a des règles qu'on peut énoncer : les tests passent, le tableur s'ouvre et recalcule, le total est bien la somme des lignes, les chiffres d'entrée sont ceux de la source. Pas de juge, pas de doute.

Constaté

Nodal regarde le monde

Envoyer un message, créer un événement, écrire une ligne dans une table : Nodal relit ensuite, par le même connecteur, que la chose existe bien — ou garde l'accusé de l'API quand relire n'est pas possible (un bot Telegram ne relit pas son propre message). Et si ni l'un ni l'autre n'existe, il le dit : « issue inconnue », jamais « envoyé ».

Jugé

Tes relecteurs

Rédiger, rechercher, recommander, choisir la bonne méthode : pas de vérité machine. Ce sont des relecteurs — que tu choisis, sur les modèles que tu veux, 0 à 3 par type de tâche — qui jugent, en voyant les faits de la machine.

Ton exemple : « le fichier Excel est créé, mais les calculs sont-ils bons ? »

La frontière ne passe pas entre « fait » et « bien fait ». Elle passe à l'intérieur de « bien fait » :

machinele fichier s'ouvre et recalcule, aucune formule en #REF! ou #DIV/0!
machinela colonne Total est bien la somme des lignes ; la marge est bien (prix − coût) / prix sur chaque ligne
machineles chiffres d'entrée sont ceux du CSV que l'agent a réellement ouvert (Nodal sait ce qu'il a lu)
machineun second calcul indépendant, par un autre chemin, donne le même résultat
relecteur« est-ce la bonne façon de calculer la marge pour ce client ? » — ça, c'est un jugement

Et le relecteur a deux moments, pas un : avant, il peut proposer les règles que la machine vérifiera (« Total = Σ lignes, entrées = source ») — c'est toi qui les approuves ; après, il juge ce qui reste, en voyant ce que la machine a constaté. Un relecteur est bon pour écrire cette liste ; il est médiocre pour relire 400 lignes de tableur à l'œil.

Vérifier

La promesse : un agent ne peut plus déclarer un succès que rien ne prouve.

  1. Tu configures une fois, sur la fiche du projet ou du type de livrable, ce qui prouve qu'il est bon — des commandes (pnpm typecheck puis pnpm test, du plus rapide au plus long) ou des règles (« Total = Σ lignes »). Tu les valides d'un geste. Personne d'autre que toi ne peut les changer — pas même un agent.
  2. Après chaque travail, Nodal vérifie tout seul, dans l'ordre, et s'arrête à la première chose qui casse. Vert = prouvé. Rouge = pas fini, quoi qu'en dise l'agent.
  3. Les relecteurs reçoivent les faits : ce que la machine a constaté part avec la demande de relecture. Ils jugent sur ce qui a tourné, pas sur ce que l'agent raconte.

Relire

La promesse : tu décides qui relit quoi, et combien — et une relecture veut dire quelque chose.

  1. Tes relecteurs sont des agents que tu crées comme les autres (la recette « Relecteur » existe déjà), chacun sur le modèle de ton choix. Nodal exige des familles de modèles différentes entre eux et avec l'agent relu : deux instances du même modèle partagent les mêmes angles morts — c'est mesuré, pas une opinion.
  2. Par type de tâche, tu fixes 0, 1, 2 ou 3 relecteurs. Zéro = la machine seule, dit tel quel. La recherche donne la plage : le deuxième relecteur apporte beaucoup, le troisième encore un peu, le quatrième presque rien.
  3. Ils relisent en parallèle, une seule fois chacun, sans parler à l'agent. Une correction déclenche une relecture fraîche — jamais une conversation qui s'éternise : les études montrent qu'au-delà d'un passage, les relecteurs inventent des problèmes quand les vrais sont épuisés.
  4. Un verdict est fondé ou il n'existe pas : chaque constat bloquant cite sa preuve — la ligne, la cellule, le message. Un doute sans preuve est remonté, il ne bloque pas.

Corriger

La promesse : une erreur déclenche une réparation courte et encadrée — jamais une boucle infinie, jamais du cassé livré.

  1. Preuve rouge → une chance de réparer. Nodal remet l'erreur sous les yeux de l'agent, une fois — pas 50 Ko de logs, mais l'extrait utile. Il répare, Nodal re-vérifie.
  2. Encore rouge → on s'arrête proprement. Le job finit en « bloqué » avec l'erreur exacte, au lieu de tourner en rond en brûlant ton abonnement.
  3. La relecture aussi est bornée : deux cycles correction → relecture fraîche maximum, comptés par la machine. Après, on te remonte le problème au lieu d'insister.

Ce que tu verras dans Nodal

1

Sur la fiche projet (dès ①) : les commandes de preuve et les règles, avec ton geste de validation.

2

Dans les réglages de l'espace (dès ①) : quelles façons de travailler sont sous vérification — l'outil de code, les agents Claude Code / Codex, les outils fichiers, les commandes — une case chacune, à toi de choisir. Puis (④) : pour chaque type de tâche, le nombre de relecteurs requis et lesquels, avec un avertissement si deux partagent la même famille de modèle.

2b

Dans le détail d'un run (dès ①) : les preuves qui ont tourné — commande, durée, résultat — lisibles pendant la semaine d'observation, avant que la garde ne décide quoi que ce soit.

3

Sur chaque run, une fin honnête :

Succès vérifié — prouvé par la machine, relu par N Succès non vérifié — rien de configuré, dit tel quel Succès non relu — 0 relecteur pour ce type, dit tel quel Bloqué — une preuve casse ou un relecteur a un bloquant fondé, voici lequel

Les règles du jeu (tes décisions du 30/08 et du 03/09)

  • Quand des relecteurs divergent : un bloquant fondé de n'importe lequel suffit à bloquer ; approuver exige que tous aient rendu et qu'aucun bloquant fondé ne reste. Un doute sans preuve remonte, ne bloque pas. (D5)
  • Le réglage des relecteurs suit ce que la tâche demande de produire — code, fichier Office, action sortante, document, autre — pas l'agent qui la fait. (D6)
  • Les règles de preuve : un agent peut en proposer, seul toi approuves. (D7)
  • C'est toi qui choisis quelles façons de travailler sont vérifiées — par un réglage, pas par un choix du produit. Toutes le sont par défaut. (D8)
  • Il faut une interface dès la première PR : configurer les preuves et les lire, sans attendre la garde. (D9)
  • C'est toi qui approuves les commandes et les règles, une fois, et à chaque modification. Jamais de question à chaque exécution.
  • Une seule réparation automatique par preuve rouge — chaque tour coûte ton abonnement.
  • Les preuves tournent en fin de travail, pas après chaque petite écriture.
  • Un projet sans commande ne bloque rien : le run réussit mais s'affiche « non vérifié », sans ambiguïté.

Ce que la lecture a ajouté — v5 (02/09) et v6 (03/09)

Le plan v4 tenait déjà l'essentiel : la preuve lancée par la machine, une condition d'arrêt testable, des boucles bornées. Deux journées de lecture — Osmani, Datadog, Faros, Anthropic, puis six papiers de recherche — ont ajouté ceci.

v5 · fail fast — Osmani, Faros

Plusieurs commandes, de la moins chère à la plus chère

Arrêt au premier rouge : l'agent reçoit l'erreur la plus précise en premier, et tu ne paies la suite longue que quand les vérifications rapides sont passées.

v5 · feedback lisible — DeepSeek Harness, Faros

L'extrait d'erreur, pas le log brut

Commande, code de sortie, dernières lignes, lignes d'erreur, chemin du log complet. Un module, testé sur les cas limites.

v5 · mesurer avant d'imposer — Anthropic, Datadog

Une semaine d'observation avant d'activer la garde

La preuve tourne sur tes vrais jobs sans changer leur issue ; les seuils de la garde se calent sur les chiffres.

v6 · livrables non-code — Relational Conformance (2607.14155)

La machine vérifie des règles, pas seulement l'existence d'un fichier

Des livrables chacun valides et contradictoires ensemble : la réponse du papier est un manifeste de règles vérifiées mécaniquement, recalculées par un chemin indépendant, sans LLM. C'est le modèle des « règles » ci-dessus.

v6 · tests qui ne testent rien — All Smoke, No Alarm (2606.18168)

« Tests verts » écrits par l'agent ne suffit pas

80 % des tests écrits par des agents de code n'assertent rien de fort (33 596 PR étudiées). Nodal contrôlera que les tests ajoutés vérifient quelque chose.

v6 · combien de relecteurs — Multi-Agent Verification (2511.16708), PoLL (2404.18796)

0 à 3, différents

Gains mesurés de +14,9 / +13,5 / +11,2 points pour les relecteurs 2, 3, 4 : rendements décroissants. Un panel de trois familles de modèles bat un seul gros juge, sept fois moins cher. D'où : 1 à 3, de familles distinctes.

v6 · parallèle, pas en boucle — More Rounds, More Noise (2603.16244)

Une relecture par passage, jamais une conversation

Les rounds de relecture successifs dégradent le résultat (+62 % de faux positifs) : les relecteurs fabriquent quand les vraies erreurs sont épuisées. Donc en parallèle, une fois chacun, contextes séparés.

v6 · verdict fondé — Adversarial Review (2608.18167)

Un bloquant cite sa preuve

+10 points quand le relecteur doit citer le code ; l'échec typique est le « faux consensus » — céder sans preuve. Chaque constat bloquant cite ligne, cellule ou message ; un doute sans preuve ne bloque pas.

PR① est codée — ce qui existe maintenant (04/09)

Les 24 tickets du découpage sont sur la branche feat/verifier-corriger-pr1, chacun avec ses tests sur données réelles et ses mutations rouges. Six passes Codex, CI verte, pas encore mergée (la #45 passe devant).

Ce que tu pourras faire, une fois la stack redémarrée (elle appliquera quatre migrations) :

  • Sur la fiche d'un projet dans l'onglet Code : déclarer de une à cinq commandes de preuve (« pnpm typecheck », « pnpm test »…), dans l'ordre, puis les approuver — avec l'avertissement en toutes lettres, parce que ces commandes exécutent du code du dépôt avec ton compte. Un projet non approuvé n'exécute rien.
  • Dans Settings : choisir quelles façons de travailler sont vérifiées (outil de code, agents Claude Code / Codex, outils fichiers, commandes). Décocher demande confirmation ; recocher, non.
  • Dans le détail d'un run : lire ce que la preuve a fait, commande par commande (rang, code de sortie, durée, verdict) — et, quand elle n'a pas tourné, pourquoi : surface décochée, projet sans commandes, tour de chat.

Ce que Nodal fait tout seul, sans rien bloquer (c'est la phase d'observation) :

  • Avant qu'un outil ou un agent CLI écrive dans un projet, il le note. Une écriture pendant la preuve, ou par un autre job, est vue : le projet reste « à prouver ».
  • À la fin d'un job, il lance les commandes approuvées et garde chaque résultat. Un projet rouge finit quand même « terminé » — pour l'instant on mesure, on n'impose pas.
  • Le message de fin part par une boîte d'envoi : commis avec le statut, envoyé juste après, repris par le cron si le runner tombe entre les deux, trois essais au plus, et tu es alerté quand un envoi est définitivement refusé.

Bugs existants corrigés au passage (trouvés par les tests, pas par une revue) :

  • Une livraison pouvait se perdre si le runner tombait entre « terminé » et l'envoi.
  • Une course perdue (job fini par un autre chemin) envoyait quand même le message.
  • L'alerte au propriétaire visait toujours Telegram, même sur un agent Discord seul.
  • Un job relancé depuis le tableau de bord ne pouvait plus se terminer (trace d'un premier passage).

Où en est la relecture (04/09, soir) :

  • PR #46 ouverte, quatre passes Codex. La première a trouvé deux vrais trous : les vingt outils Office (Word, Excel, PowerPoint) écrivaient sans être vus par la vérification, et la boîte d'envoi pouvait, dans un cas précis, laisser un autre runner écraser une tentative en cours — les deux sont fermés. Vérifier sans rien configurer (v7 — 05/09)

L'essai à l'écran a montré le vrai trou, et il change l'ordre de tout le reste. La vérification de PR① exige d'être configurée à l'avance, sur un écran. Or une tâche arrive le plus souvent par Telegram : pas d'écran, aucun moment pour cocher quoi que ce soit. Et personne ne devrait avoir à connaître des commandes pour qu'un travail soit vérifié.

Le principe qui remplace la configuration : ce qu'il faut vérifier se déduit de ce qui a été produit et de ce qui a été demandé. La seule ligne qui compte est avec pouvoir / sans pouvoir. Ouvrir un classeur, constater qu'une formule recalcule, vérifier qu'un message est bien parti : rien de tout cela n'exécute du code du dépôt, donc rien ne demande d'approbation. Lancer pnpm test, si : ça s'approuve une fois par projet, et l'approbation peut se donner dans le canal d'où vient la demande.

Pour les ingénieurs — la mécanique qui tient les promesses

Tout ce qui suit est la tuyauterie. La source complète : docs/plans/verifier-corriger.md (v6).

Pourquoi c'est plus dur qu'il n'y paraît (les 4 pièges trouvés par Codex)
  • Savoir qu'un livrable a été modifié : le checkpoint se déclenche AVANT l'outil, même en lecture seule — il ne prouve rien. Remplacé par une « intention de mutation » écrite en base AVANT chaque écriture.
  • Deux agents en même temps : générations sale/vérifiée par (job, livrable) + un compteur global ; verrous en base dans un ordre fixe ; tests de course à deux connexions réelles.
  • Toutes les sorties passent par une porte : 4 chemins marquent un job « réussi » aujourd'hui (dont un cron qui écrit en direct — vérifié encore le 02/09). Une primitive unique, résultat typé, livraison interdite hors succès.
  • La commande de preuve est un pouvoir : d'où l'approbation par empreinte — seule la révision exacte validée s'exécute, liste, ordre et règles compris.
v6-A (v6.1) · Livrable, pas projet — identité générique, deux modèles d'état, manifeste unique
  • Identité (job_id, deliverable_type, canonical_key), clé opaque produite par un canonicaliseur par type ; verrous en ordre (type, clé). PR① ne définit que code_project (= projectKey, déplacé dans packages/shared) ; les autres types sont réservés sans clé provisoire — type sans canonicaliseur ⇒ refus typé.
  • Livrables mutables (code, fichier, document) : générations sale/vérifiée (v4). Livrables atomiques (action sortante) : machine d'état prepared → attempted → confirmed | rejected | outcome_unknown, clé d'idempotence posée AVANT l'appel ; confirmed = vérifié, rejected = pas fini, outcome_unknown = « non vérifié », jamais un succès.
  • Constat d'une action : relecture indépendante quand le connecteur a une lecture (Airtable, Gmail, Calendar, Sheets, Notion, Drive — inventaire du 03/09), accusé structuré sinon (Telegram : message_id), ni l'un ni l'autre ⇒ issue inconnue.
  • Manifeste unique par cible : commandes + invariants + contexte, un hash, une approbation atomique (D1) ; un agent propose, l'owner approuve (D7). Recalcul sans les helpers du générateur.
  • Pour document : un registre de lectures deliverable_reads (ressource, digest, tool-call) — ni task-ledger ni STATE_CHANGING_TOOLS ne tracent une lecture. Lot ⑤.
v6-B · Contrôle d'oracle sur les tests écrits par l'agent
  • Preuve verte + diff ajoutant des fichiers de test ⇒ contrôle syntaxique des assertions (taxonomie W1→S1 du papier 2606.18168) ; run marqué green_weak_oracle si les tests ajoutés n'assertent rien. Sévérité décidée après observation. Mutation : option ultérieure.
v6-C · Relecteurs configurables — pool, politique, exécution
  • Un relecteur = un agent (recette « Relecteur », lecture seule, porte review_verdict), sur le modèle choisi. Pool = les agents relecteurs de l'espace. Aucune nouvelle entité (invariant #1).
  • Politique d'espace, en base : par type de livrable, 0-3 relecteurs requis, lesquels (liste ordonnée ou « n'importe lesquels du pool ») ; familles de modèle distinctes exigées entre eux et avec le codeur — l'UI avertit, le harnais refuse (REVIEW_POOL_SAME_FAMILY).
  • Un seul flux : la revue est une étape de la primitive terminale, après la preuve machine — review_pending → requestReview(snapshot_id, policy) crée exactement N jobs job_protocol='review' → agrégation. Un agent ne peut plus initier un relecteur isolé : request-review appelle la primitive, la délégation directe est refusée.
  • Snapshot gelé par type : deliverable_snapshots (digest sha-256 ; blob copié pour fichiers et documents, HEAD+diff pour le code, reçu normalisé pour les actions). Les N jobs référencent le même snapshot_id.
  • Cycles : review_cycles — un cycle = N verdicts sur un snapshot, clos une fois ; review_rounds += 1 par cycle exigeant correction, jamais par verdict ; à 2 ⇒ escalade.
  • Relecteur en échec (budget, panne, timeout) : fail-closed — pas d'approbation ; une relance du seul job manquant ; sinon REVIEW_INCOMPLETE, escalade humaine, aucun cycle consommé.
  • Familles : le catalogue n'en a pas (vérifié) ; ajout de modelFamily (anthropic:claude, openai:gpt…), indépendant du transport, obligatoire pour être relecteur ; famille inconnue ou dupliquée ⇒ refus typé.
  • Agrégation = D5. Calibration (taux d'accord avec l'owner sur la fiche du relecteur) en v2.
v6-D · Un verdict fondé
  • review_verdict aujourd'hui : {file, line?, issue, severity: blocker|major|minor}. On garde blocker et on ajoute par constat kind (evidence · concern) et une citation générique (fichier:ligne, onglet!cellule, id de message, ressource+repère), obligatoire pour evidence. request_changes sans blocker fondé ⇒ REVIEW_VERDICT_UNGROUNDED.

Le modèle de données
  • Table d'état par (job, livrable canonique) : génération sale, génération vérifiée, statut, compteurs de rouge consécutif et de réparation, empreinte prouvée.
  • verification_runs = journal (vérificateur, commande, rang, code de sortie, sortie tronquée, durée) — audit et observation, jamais la décision.
  • Sur code_projects : commandes, invariants, empreinte approuvée, compteur global de modifications. Clé canonique partagée runner/web, migration de fusion déterministe.
