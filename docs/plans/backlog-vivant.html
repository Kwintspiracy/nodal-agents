③ Vérifier & Corriger — la loop de vérification PR① + v7-A CODÉES · PR #46 · 6 PASSES CODEX la plus grosse

PR① est codée, relue et verte (feat/verifier-corriger-pr1, PR #46) : 24 tickets, 6 passes codex review, CI verte. Quatre bugs existants fermés au passage. La première brique de v7 est livrée le 05/09 : chaque outil déclare CE QU'IL PRODUIT, un tableur écrit dans un dépôt ne relance plus les tests du dépôt, et un outil qui ne déclare rien est refusé plutôt que rangé « en code » par défaut. La passe 5 a trouvé deux vrais défauts dans cette brique (le repli du seam, l'ordre des verrous déduit du type) : les deux sont fermés. L'essai à l'écran avait montré le vrai trou, et il change l'ordre du reste : la vérification exigeait d'être configurée à l'avance sur un écran, alors qu'une tâche arrive le plus souvent par Telegram, sans écran ni moment pour cocher quoi que ce soit. D'où v7 « vérifier sans configurer », remontée devant tous les autres lots : le type de livrable se déduit de ce qui est produit ; tout ce qui se vérifie sans exécuter de code du dépôt (un tableur s'ouvre et recalcule, un message est bien arrivé) tourne toujours, sans réglage ; les commandes d'un projet sont découvertes et approuvées dans le canal d'où vient la demande ; et les exigences de la demande deviennent des critères vérifiables. Détail et découpage en quatre PR dans le plan, § v7 ; la version lisible est le point d'arrêt. Le code devient le premier vérificateur : Nodal lance lui-même les commandes de preuve du projet après le travail d'un agent, et un agent ne peut plus dire « fini » si c'est rouge. Test rouge → une réparation, pas plus ; encore rouge → « bloqué », avec l'extrait d'erreur. Le plan v6 = la v4 (six passes Codex, D1-D4 tranchées) + v5 (commandes graduées, extrait d'erreur lisible, semaine d'observation) + v6 du 03/09, six papiers lus : ça vaut pour tous les livrables, pas seulement le code (état par livrable, règles déclarées vérifiées par la machine, relecture après écriture sur les connecteurs), et tu définis tes relecteurs : 0 à 3 par type de tâche, familles de modèles distinctes, en parallèle une fois chacun, verdict fondé sur des citations. D5-D7 tranchées le 03/09. Puis cinq passes Codex sur le plan (7 à 11) : 14 bloquants fermés — dont un bug qui existe aujourd'hui : un crash entre « job terminé » et l'envoi au canal perd le résultat à jamais ; fermé par une outbox de livraison qui entre en PR①. Boucle sur plan close.

Séquence : PR① fondations (faite) → v7-A le type de livrable vient de l'outil (faite) → v7-B vérifier un document et un envoi, sans pouvoir → v7-C découvrir les commandes et les faire approuver dans le canal d'origine → v7-D les critères tirés de la demande → observation → garde active → runtime CLI → revue bornée.
