Le livrable est la page

Nodal montre son processus et cache son produit. On inverse les deux.

Aujourd'hui, un travail fini se présente comme une ligne de statut : un identifiant, un badge, et un pavé de texte.

Demain, il se présente comme la chose qu'il a produite : le tableau, la page, le diff, le message parti. Le déroulé passe derrière, à un clic.

La question d'aujourd'hui

« Le job 4c06 est completed. Qu'est-ce qu'il a fait, au juste ? »

La question de demain

« Voilà le budget 2027. Il s'ouvre, trois onglets, aucune formule cassée. »

Ce n'est pas une réorganisation de menus. C'est un renversement : la page d'un travail n'est plus une fiche d'exécution, c'est le livrable lui-même, rendu selon sa forme. Trois écrans suffisent à le montrer.

Ce qu'il faut regarder : le canal reçoit le livrable, pas un statut. Même vocabulaire que l'écran, en trois lignes. C'est la même donnée rendue plus petit, pas un second système à entretenir.

Ce que ça coûte, dit franchement

  • Trois écrans fusionnent en un. Jobs, Code et le détail d'un run deviennent « Travaux ». Le Chat reste, mais il cesse d'être l'endroit où on va chercher un résultat.
  • Il faut un rendu par forme. Cinq pour commencer : document, tableur, page, code, envoi. Chacun est un composant, aucun n'est difficile pris seul.
  • Les contrôles doivent parler français. « ✓ le fichier s'ouvre » au lieu de pnpm test — exit 0. C'est du travail d'écriture autant que de code.
  • On perd le tableau de bord d'exploitation. Qui veut voir les statuts bruts, les relances, les erreurs, devra aller dans un écran technique dédié. C'est le prix, et je le crois juste : cet écran sert une fois par mois, l'autre sert dix fois par jour.

Ce qui rend ça possible aujourd'hui et pas il y a une semaine : chaque outil déclare désormais ce qu'il produit. La forme d'un livrable n'est plus à deviner, elle est écrite en base avant même l'écriture. Il ne manque que le rendu.

Ce qu'il me faut de toi

Un mot sur le parti pris, pas sur les détails : est-ce que « le livrable est la page » est la bonne direction ?

Si oui, je commence par l'écran 1 et deux formes — tableur et code — parce que ce sont celles que tu produis le plus. Le reste suit sans nouvelle décision. Si non, dis-moi ce qui cloche dans les images, c'est fait pour ça.

Pour les ingénieurs : d'où vient chaque morceau

La forme d'un livrable existe déjà : le champ obligatoire posé ce matin sur chaque cible de mutation. Il porte aujourd'hui code_project et office_file ; la liste s'étend à document, page, outbound_action.

La liste des fichiers produits se lit dans la table d'état par livrable, écrite avant chaque écriture. C'est la même source que la rangée de pastilles de DeepSeek Harness, et elle est plus fiable que l'extraction par expressions régulières d'Hermes.

Le rendu par forme suit le contrat de dsh : l'outil déclare une carte, l'écran la traduit, et un outil n'importe jamais un type d'interface. Six cartes chez eux, cinq chez nous pour commencer.

Les contrôles en français viennent du moteur de preuve déjà livré. Ce qui change est la couche d'affichage : un code de contrôle plus une durée, jamais la ligne de commande brute.

La carte du canal réutilise l'envoi de cartes à boutons qui existe pour les approbations, neutre vis-à-vis du canal.
