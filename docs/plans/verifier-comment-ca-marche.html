Comment Nodal vérifie

Tout le chantier en une page, sans jargon. Tu as trouvé deux défauts en cinq minutes d'écran. Les deux sont corrigés. Restent deux choses à trancher, et une question ouverte sur Telegram.

Le problème, en trois phrases

Aujourd'hui, un agent finit son travail et écrit « c'est fait ».

Personne ne vérifie que c'est vrai.

On veut que Nodal le vérifie lui-même, avant de te dire que c'est terminé.

Comment ça marche

1

Un agent s'apprête à écrire dans un dossier. Nodal note : ce projet a changé.

2

L'agent termine son travail.

3

Nodal relance la vérification de ce projet, et s'arrête à la première chose qui ne va pas.

4

Nodal garde le résultat. Tu le lis dans le détail du run.

Tu ne donnes rien à chaque tâche. La vérification est attachée au projet, une fois. Ensuite, tous les jobs qui touchent ce projet la relancent tout seuls. Ma première version de cette page laissait croire le contraire.

Pour l'instant, rien n'est bloqué. Même si une commande échoue, le travail est marqué terminé. C'est voulu : on regarde d'abord ce que ça donne pendant une semaine sur tes vrais jobs. Bloquer viendra après, avec des seuils tirés de ces chiffres.

Et si je demande un fichier Excel ?

C'est la question que tu as posée. Voici où on en est le 5 septembre, en deux temps.

Ce qui marche maintenant : ton tableur existe pour Nodal. Il a sa ligne, son identité, et il n'est plus confondu avec le code. Le détail du run le nomme et dit la vérité : « pas encore vérifié ». Il ne t'envoie plus chercher un réglage qui n'existe pas.

Ce qui manque encore : la vérification elle-même. Vérifier un tableur, ce n'est pas lancer une commande, ça n'aurait aucun sens. C'est autre chose : le fichier s'ouvre vraiment, les formules recalculent, les totaux tombent juste, les chiffres du rapport concordent avec ceux du tableau. Rien de tout cela ne se tape dans un champ. Nodal le fait, ou ne le fait pas.

Et rien de tout cela ne fait tourner du code du projet. Donc rien de tout cela n'aura jamais besoin de ton approbation. C'est le lot suivant.

Et quand je passe par Telegram ?

C'est le cas qui compte, et c'est celui qui casse tout ce que j'ai livré. Tu écris « crée-moi ceci » depuis Telegram. Tu n'as pas d'écran. Il n'y a aucun moment où tu peux cocher quoi que ce soit. Or aujourd'hui, sans configuration, rien ne se vérifie.

Donc la vérification ne doit pas se configurer : elle doit se déduire. De ce que tu as demandé, et de ce que l'agent a produit. La bonne ligne de partage n'est pas « du code ou pas du code », c'est celle-ci :

Sans pouvoir — aucune permission

Nodal ouvre le fichier qu'il vient de produire, recalcule, compare les totaux, relit le message qu'il a envoyé. Il ne lance rien qui vienne du dépôt. Ça peut donc tourner toujours, sans réglage et sans te déranger.

Avec pouvoir — une permission, une fois

Lancer les tests d'un projet exécute du code du dépôt. Là, il faut ton accord — mais une seule fois par projet, et Nodal peut te le demander dans Telegram, avec deux boutons. Ce mécanisme existe déjà pour les autres approbations.

C'est écrit dans le plan sous le nom v7, « vérifier sans configurer », découpé en quatre livraisons. Je l'ai remontée devant tous les autres lots.

Les deux défauts que ta question a mis au jour — corrigés

corrigé le 5 septembre

1. L'écran ne te proposait rien

Tu as cliqué « Add a command » et tu n'as pas su quoi mettre. Tu avais raison : rien ne te le disait.

Maintenant Nodal lit le projet et te montre ce qu'il y trouve. Un seul bouton, « Add these ». Et à côté de chaque commande, ce qu'elle lance vraiment — parce qu'un projet peut appeler n'importe quoi depuis un script nommé « test », et que tu dois le voir avant d'approuver.

Un dossier sans manifeste connu ne propose rien, et le dit. Il n'invente pas une commande qui n'existe pas.

corrigé le 5 septembre

2. Un tableur déclenchait les tests du code

Si un agent écrivait un fichier Excel dans un projet de code, Nodal marquait le projet comme modifié et relançait ses tests. Le code n'avait pas bougé d'une ligne.

La cause : une seule sorte de livrable était branchée, le projet de code. Tout ce qu'un agent écrivait y était rangé, faute de mieux.

Désormais chaque outil déclare ce qu'il produit. Un tableur est un tableur. Il a sa propre ligne, sa propre identité, et il ne relance plus les tests du dépôt qui l'héberge. Le dépôt, lui, reste marqué dès qu'un fichier texte y est écrit : c'est le côté prudent, une vérification de trop coûte moins cher qu'une livraison jamais vérifiée.

Ce que Nodal ne sait pas encore faire, et qu'il dit clairement à l'écran : vérifier le tableur lui-même. Il s'ouvre ? Les feuilles demandées existent ? Aucune cellule en erreur ? C'est le lot suivant.

À toi de décider

à moitié fait

1. Rien à configurer du tout

Fait : Nodal lit le projet, trouve ses commandes, te les montre. Un bouton les ajoute.

Reste : quand tu lances une tâche depuis Telegram, tu n'as pas cet écran. Nodal doit te poser la question là où tu es : « ce projet veut lancer ceci pour se prouver, tu es d'accord ? », avec deux boutons dans la conversation. Telegram sait déjà afficher des boutons. Ce qui manque est le fil entre « une preuve attend » et « cette tâche vient de ce canal ».

fait le 5 septembre

2. Ranger chaque chose dans sa catégorie

Un fichier Excel écrit par un agent est un livrable à part, pas une modification du projet de code qui l'héberge. Il ne relance pas les tests. En attendant son propre vérificateur, son état est « pas encore vérifié », dit tel quel.

C'est livré. Chaque outil déclare ce qu'il produit, et un outil qui ne le déclare pas est refusé plutôt que rangé au hasard. Codex a relu, a trouvé deux vrais défauts dans ma première version, et les deux sont corrigés.

3. v7 en premier, et la première brique est livrée

J'ai remonté « vérifier sans configurer » devant tous les autres lots, et repoussé la semaine d'observation derrière : sans v7, elle ne mesurerait que les projets configurés à la main, c'est-à-dire aucun.

Quatre livraisons, la première est faite : le type de livrable se déduit (fait) ; les vérifications sans pouvoir ; la découverte des commandes et l'approbation dans le canal ; les critères tirés de ta demande. J'enchaîne sur la deuxième sauf avis contraire.

4. Deux dossiers qui pointent au même endroit

Si le même dossier est attaché deux fois — une fois directement, une fois par un raccourci — le même projet compte double. Les commandes sont d'un côté, les résultats de l'autre.

Ma recommandation : l'interdire au moment où on attache, avec un message qui nomme les deux dossiers. L'autre option, accepter deux identités, est logique mais déroutante à l'écran.

Sur quoi c'est basé

Six articles de recherche et la façon dont d'autres harnais s'y prennent. Trois idées en sont sorties, et ce sont elles qui structurent tout le reste.

  • La machine d'abord. Tout ce qui peut se vérifier sans jugement se vérifie sans LLM.

Le détail technique (si tu veux le voir)

Le plan complet, avec le suivi lot par lot : Vérifier & Corriger. La branche est feat/verifier-corriger-pr1, la pull request la #46.

  • L'identité d'un projet est son chemin, normalisé une seule fois dans le code partagé (projectKey). C'est ce qui a occupé trois des quatre relectures.
  • Une seule porte de sortie pour les jobs (finalizeJobSuccess), et une règle d'architecture qui interdit d'en ouvrir une autre.
  • L'envoi au canal passe par une boîte d'envoi : l'intention est enregistrée avec le statut, l'envoi suit, et le cron reprend ce qui manque.
  • Les tests de concurrence tournent sur un vrai Postgres à deux connexions. Ils passent sur Linux à chaque run ; le runner Windows de GitHub ne peut pas les faire tourner, parce que PostgreSQL refuse de démarrer sous un compte administrateur.
  • Reste aussi, côté ménage : deux copies de règles à retirer dans le runner, et un geste manquant pour effacer toutes les commandes d'un projet.
