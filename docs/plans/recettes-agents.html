Recettes d'agents

Un agent déjà équipé pour ce qu'on veut en faire — un à la fois, jamais une équipe livrée clés en main.

PROPOSITION v2 · 29/08/2026 · à valider avant d'écrire une ligne

Ce que la v1 se trompait à proposer

La première version créait trois agents d'un coup — un lead, un développeur, un relecteur. Elle livrait une structure d'équipe que personne n'avait demandée, et trois objets à comprendre avant d'en avoir utilisé un seul.

Une recette décrit un agent. Si quelqu'un veut une équipe, il ajoute un second agent quand le premier lui a montré ce qui lui manquait — pas avant.

Le problème

Créer un agent aujourd'hui, c'est remplir un formulaire : un nom, un modèle, un rôle. Puis aller chercher les skills dans un écran, les connecteurs dans un autre, le dossier de travail dans un troisième. Chaque champ se comprend ; l'assemblage, non.

Personne ne sait, en arrivant, qu'un agent qui code a besoin d'un dossier attaché, ou qu'un agent qui coordonne a besoin d'un modèle capable d'appeler des outils. Ce sont des règles qu'on apprend en se trompant.

Ce que je propose

Une recette : la description déclarative d'un agent équipé pour une activité — son rôle, ses skills, ses outils, le type de modèle qui convient, et ce qu'il lui faut d'autre pour ne pas être cassé.

Nodal-Agents ne shippe pas d'agents. Ce qui est livré est un fichier dans packages/catalog. Rien n'existe en base avant le clic : une recette pré-remplit l'écran de création qui existe déjà. Tout reste modifiable avant de valider, et l'agent obtenu est un agent ordinaire.

Le catalogue

Rangé par équipe — pas comme un classement, comme une suggestion. Voir « Dev team » apprend qu'il existe une forme qui marche ; rien n'oblige à la reproduire, ni à la compléter.

Que doit faire cet agent ?

Les équipes ci-dessous sont des suggestions. Rien n'oblige à les créer en entier — ni dans l'ordre.

Dev team Chef d'équipe → Développeur + Relecteur

Le chef reçoit la demande et la confie. Le développeur écrit. Le relecteur vérifie, avec un modèle différent — deux instances du même modèle partagent les mêmes angles morts.

Les équipes s'ajoutent avec le catalogue. « Partir de zéro » reste le dernier choix : une recette ne remplace pas le formulaire, elle le remplit.

Le groupe suggère, il n'agit pas. « Dev team » a un nom d'équipe et montre sa forme — qui reçoit, qui écrit, qui vérifie — parce que c'est une connaissance utile que personne n'a en arrivant. Mais il n'y a pas de bouton qui crée les trois. Chaque rôle se crée seul, dans n'importe quel ordre, et une équipe à un seul membre est un usage parfaitement normal. Ce qui est déjà dans l'espace est signalé, pour informer : pas pour réclamer d'être complété.

Ce que fait le clic

Il ouvre l'écran de création, déjà rempli. Ce que la recette a posé est signalé comme tel, et se modifie avant de valider.

Une recette peut rendre un champ obligatoire. C'est là sa vraie valeur : elle sait ce qui casse quand on l'oublie.

Et si quelqu'un veut une équipe ?

Il crée un développeur. Il s'en sert. Le jour où il veut que le travail soit relu, il crée un relecteur, puis un chef d'équipe à qui il rattache les deux — avec les écrans qui existent déjà.

Une recette peut le dire sans le faire : la fiche « Chef d'équipe » indique qu'il lui faut des agents à qui déléguer, et propose ceux qui existent déjà dans l'espace. Le produit suggère ; il n'assemble pas à la place de la personne.

Ce que je ne fais pas

Écarté Pourquoi
Créer plusieurs agents d'un clic non C'était la v1. Ça impose une structure que personne n'a choisie, et livre des objets à comprendre avant d'en avoir utilisé un seul.
Un tunnel de questions non Une recette pré-remplit un écran existant. Ajouter des étapes pour créer un agent serait un recul.
Une recette qui se met à jour non Ce serait un lien vivant entre le produit et les agents d'un utilisateur — ce que l'invariant interdit.
Dix recettes d'un coup plus tard Deux ou trois, polies, valent mieux qu'un catalogue à moitié juste.

Ce que je vérifie avant de dire que c'est fini

installation neuve → « nouvel agent » → équipe Dev team → Développeur → l'écran s'ouvre pré-rempli, le dossier reste à choisir → création → un message à cet agent → il écrit dans le dossier choisi, et nulle part ailleurs.

Et le contrôle qui compte le plus : l'agent obtenu doit être indiscernable d'un agent monté à la main. Même écran d'édition, même suppression, aucune trace de la recette en base. Si une recette laisse quoi que ce soit derrière elle, elle a franchi la ligne.

Trois décisions qui t'appartiennent

1. Le mot « recette »

Il dit bien qu'on décrit sans exécuter, mais il évoque la cuisine. « Modèle » est déjà pris par les LLM. « Profil » était le mot du backlog.

Je penche pour aucun nom à l'écran : une question, « Que doit faire cet agent ? », et des choix. Le mot ne servirait qu'entre nous et dans le code.

2. Quelles recettes en premier

Je propose Développeur, Relecteur, Chef d'équipe — le trio dont le produit sait déjà tout faire, et celui dont les pannes de l'été sont les plus fraîches.

Si une autre équipe est plus demandée que la Dev team, elle passe devant : la première donnera sa forme aux suivantes.

3. Un champ obligatoire, jusqu'où ?

La recette « Développeur » exige un dossier. C'est ce qui évite la panne du 27/08 — mais c'est aussi le produit qui refuse de créer un agent tant qu'une case n'est pas remplie.

Je recommande de l'exiger, en expliquant pourquoi à l'écran plutôt qu'en bloquant en silence. Un agent qui code sans dossier n'est pas à moitié configuré : il est cassé.

État au 30/08 · PR #45, huit passes Codex

Construit — « Nouvel agent » ouvre la question, Start from scratch en premier, les trois profils ensuite, la Dev team en note de bas de page. Choisir un profil ouvre un panneau de détail (rôle, skills avec leur description, outils bloqués, autonomie, ce qui reste à fournir) avant le formulaire pré-rempli. Décisions 1 et 2 prises comme recommandé ; la 3 (dossier obligatoire) est reportée à une PR de suite.

Ce que les revues ont corrigé dans le plan lui-même. Le plan disait « appliquer le profil juste après la création » : faux. Un membre non propriétaire choisissant Code reviewer obtenait un agent créé puis un verrou refusé — un agent capable d'écrire, portant le nom d'un qui promettait de ne jamais écrire. Création et profil sont maintenant une seule transaction, autorisée avant que la ligne existe, annulée si un skill promis manque. Corollaire découvert en chemin : le premier orchestrateur d'un workspace en devient la racine (rootAgentId + rootGrants), et un rollback par simple suppression laissait les grants réécrits.

Aussi corrigés : les skills système introuvables hors du premier workspace (chaque install LAN), le slug d'un second agent du même profil (developer-2), le catalogue entier — corps Markdown compris — expédié au navigateur par le panneau, un next-env.d.ts muté par next dev, et la garde de conformité design (text-[Npx]) rouge sur trois composants neufs.

Refusé, huit fois de suite : Codex veut les recettes en base au nom de l'invariant #1. Le catalogue est défini comme data-as-code pour le bootstrap (packages/catalog/src/types.ts) ; le runtime ne lit jamais une recette ; l'agent créé n'en porte aucune trace. Ce point reste ouvert à ton arbitrage.
