- **C1 — bloquant — `apps/cli/src/lib/orphans.ts:68`.** La frontière accepte encore des dossiers distincts. Reproduction exécutée sur la fonction actuelle avec notre dossier `C:/install/pg-data` : les arguments `-D "C:/install/pg-data/other"`, `-D "C:/install/pg-data backup"` et `-D "C:/install/pg-data/../foreign"` produisent tous `owned: [101,102]` pour le postmaster étranger et son worker. Le `/` ou l’espace accepté ne termine pas nécessairement l’argument. Sans autre orphelin Postgres ni conflit préalable, `up.ts:309` ajoute ces PID et `up.ts:354` tue le premier s’il vit encore.

- **C2 — bloquant — `apps/cli/src/lib/orphans.ts:97`.** La recherche porte sur toute la commande, sans identifier l’argument du dossier de données. Reproduction exécutée : `postgres.exe -D C:/foreign -c external_pid_file="C:/install/pg-data/foreign.pid"` est classé `owned: [201]`. Le fichier PID externe se trouve chez nous, mais le cluster est ailleurs. Le chemin vers le kill est celui de C1.

- **C3 — bloquant — `apps/cli/src/commands/up.ts:267` et `:295`, `apps/cli/src/lib/postgres.ts:41`.** Un fichier `postmaster.pid` périmé autorise toujours la destruction d’un processus étranger. Déclenchement : son premier nombre correspond à un PID recyclé encore vivant, avec les permissions permettant de le tuer. `livePostmasterPid` vérifie uniquement son existence ; ni date de création, ni nom, ni dossier réel. Sur notre port, ce fichier l’emporte même sur un classement étranger par WMI. Sans écoute sur nos ports, la seconde sonde ajoute également ce PID. Après la tentative d’arrêt gracieux, `up.ts:354` envoie `SIGKILL` s’il vit encore. Ce chemin préexistait en partie, mais reste dans le périmètre explicitement demandé.

- **C4 — bloquant — `apps/cli/src/lib/orphans.ts:110`.** L’ascendance ne distingue pas deux générations du même PID. Déclenchement : un worker étranger survit à son parent ; le PID de ce parent est réattribué à notre postmaster. Les lignes correspondantes font classer le worker comme nôtre, sans aucune date permettant de vérifier la filiation. Le classement a été reproduit sur la fonction pure ; le recyclage réel n’a pas été provoqué. Si ce worker apparaît en premier dans la troisième sonde, sans fichier PID ni listener reconnu, il devient le PID tué.

- **C5 — important — `apps/cli/src/lib/orphans.ts:68`.** Une tabulation après un `-D` non cité n’est plus acceptée. Reproduction exécutée : `postgres.exe -D C:/install/pg-data<TAB>-p 5432` renvoie `owned: []`, contrairement à l’ancien `includes`. Sans fichier PID exploitable, notre serveur est refusé s’il écoute sur le port configuré, ou échappe au nettoyage sinon.

- **C6 — important — `apps/cli/src/lib/postgres.ts:74` et `:119`.** L’échec de la sonde est indiscernable d’une absence de processus. Déclenchement : PowerShell indisponible, erreur ou expiration sans sortie exploitable. Seul `stdout` est lu ; le statut et `stderr` sont ignorés, et le `catch` rend silencieusement `[]`. Avec un listener et sans fichier PID exploitable, `up.ts:274` affirme alors que Nodal-Agents ne l’a pas démarré. Sans listener, le démarrage continue sans signaler que la vérification a échoué.

- **C7 — important — `apps/cli/src/commands/up.ts:341` et `:376`.** Plusieurs PID Postgres sont annoncés, mais seul le premier est arrêté et vérifié. Déclenchement : troisième sonde renvoyant plusieurs processus sans port, fichier PID absent, avec un worker en première position. `find` sélectionne ce worker ; tous les autres Postgres sont ensuite sautés, ainsi que leur attente de port (`:398`). Le postmaster peut rester vivant pendant que le lanceur annonce « Orphans cleaned up » puis démarre un nouveau serveur sur le même dossier.

1. **constat** — C1 et C2 : l’attribution par ressemblance reste destructive. Aucun `realpath` ni traitement des jonctions, chemins courts ou chemins relatifs n’existe dans le classificateur. Deux alias différents du même dossier peuvent donc être refusés ; cela ne prouve pas deux installations indépendantes. Les formes longue/8.3 et absolue/relative différentes ont été reproduites comme non reconnues. Un UNC identique est reconnu. Les apostrophes sont acceptées par le classificateur, ce qui ne valide pas leur interprétation par PostgreSQL sous Windows. La casse est systématiquement effacée : sur un dossier réellement sensible à la casse, deux noms distincts seraient confondus ; ce cas filesystem n’a pas été exercé.

2. **constat** — C3. Oui, le PID étranger peut être tué. `process.kill(pid, 0)` prouve seulement l’existence du PID ; toute erreur autre que `ESRCH` le conserve également comme candidat.

3. **constat** — C4. Une chaîne de plusieurs workers Postgres est remontée. Un intermédiaire absent ou d’un autre nom coupe la chaîne et conduit au refus. Un PID parent recyclé vers notre postmaster crée au contraire une fausse filiation ; `seen` ne protège que contre les cycles.

4. **constat** — L’incertitude aboutit au kill par les correspondances C1/C2, le fichier périmé C3 et la filiation C4. Aucune identité de processus n’est revalidée juste avant `SIGKILL`, laissant aussi une fenêtre de recyclage entre observation et destruction. Les chemins non reconnus conduisent généralement à ne pas toucher au processus ; l’échec de sonde peut toutefois être contourné par le fichier PID.

5. **tient** — L’interpolation PowerShell de `$null` a été vérifiée : elle produit `101|1|`. Le parseur conserve une commande vide ; sans ancêtre reconnu, le processus est classé dans `skipped`. Avec un ancêtre reconnu, il peut être attribué par ascendance, avec la limite C4.

6. **NON TRANCHÉ** — Un `|` isolé dans la commande est conservé correctement après les deux premiers séparateurs. En revanche, sur une sortie synthétique contenant une continuation `999|1|C:/install/pg-data"`, le parseur actuel fabrique un PID 999 classé nôtre : reproduction exécutée. La production de cette sortie par un véritable `Get-CimInstance`, ainsi que l’encodage effectif PowerShell → `execa`, n’a pas été validée. L’essai via `execa` a échoué sur un refus de lecture sandbox d’une dépendance hors worktree.

7. **constat** — C6. « La sonde n’a pas répondu » et « aucun processus » rendent le même résultat, sans diagnostic distinct. Une sortie partielle n’est pas rejetée non plus sur la base du statut de la commande.

8. **tient** — Sous réserve que la sonde de port retourne le PID, hors Windows un fichier absent, illisible ou non numérique donne `null`, puis le refus `Port conflict with a process that is not ours`. Cela peut toucher notre propre serveur encore fonctionnel : c’est bien le comportement prudent assumé. Un PID de namespace différent ne correspond pas au listener hôte. Deux lancements successifs avec un fichier lisible et le bon PID ne sont pas bloqués par cette condition. Les scénarios Linux/macOS n’ont pas été exécutés ici.

9. **tient** — `up.ts:279` indique deux actions : arrêter soi-même le processus ou changer le port dans `~/.nodalai/config.json`. Un chemin de sortie est donc présent.

10. **constat** — C7. Pour le premier Postgres sélectionné, l’accusation « aucune attente » est fausse : `waitForPidDead(..., 5000)` et une vérification finale existent même sans port. Pour les autres PID Postgres, aucune destruction ni vérification individuelle n’est faite ; le démarrage peut continuer alors qu’ils vivent encore.

11. **constat** — C6. Le message affirme « which Nodal-Agents did not start » aussi bien pour un étranger établi que pour notre serveur dont la propriété n’a pas pu être déterminée. Ces situations ne sont pas distinguées.
