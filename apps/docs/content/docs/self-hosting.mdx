Nodal-Agents is self-hosted by design. The npm package bundles everything: an embedded Postgres, migrations, the AI runner, and the dashboard. No cloud account needed.

## Install

Requires **Node 24+**.

```bash
npm install -g nodal-agents
nodal-agents up
```

If npm answers with `npm warn allow-scripts …`, it skipped the install step of
the packages it lists. Nothing needs approving: `nodal-agents up` does what the
database package's step would have done. See
[Getting Started](/docs/getting-started#if-npm-prints-an-allow-scripts-warning).

The first run launches an interactive setup wizard that asks for:

1. **LLM provider** — pick a local model (Ollama, LM Studio, Jan.ai, llama.cpp, vLLM) or a remote one (Anthropic, OpenAI, OpenRouter). You can add more providers later in the dashboard.
2. **Network mode** — loopback (localhost only, no auth) or LAN (accessible on your network, requires sign-up).

Config is saved to `~/.nodalai/config.json`. Run `nodal-agents init` at any time to re-run the wizard. On an existing install it changes only what you answer (the LLM and the network mode) and keeps everything else as it was: the database password, the secrets, the ports and the sign-in settings.

## Ports

Default ports (configurable in `~/.nodalai/config.json`):

| Service           | Default port |
| ----------------- | ------------ |
| Dashboard (web)   | 3000         |
| Runner (API)      | 3001         |
| Embedded Postgres | 25432        |

If a configured port is occupied on startup, `nodal-agents up` automatically rotates to the next free port and saves the new value to config. A service is never given a port another service of the same install holds or was given, and a config that names one port for two services is refused. The dashboard opens at the resolved URL.

## Data directory

All persistent data lives at `~/.nodalai/`, or in the folder the `NODALAI_HOME` environment variable names (an absolute path). To run a second, separate instance next to your own, see [Running a second instance](/docs/reference/cli#running-a-second-instance).

```
~/.nodalai/
  config.json      # CLI configuration (ports, auth mode, secrets, the database password)
  config.json.last-good  # The version of config.json before its last change
  secrets.key      # The master key every stored credential is encrypted with
  pg-data/         # Embedded Postgres data files
  pids/            # PID files for runner + web (used by `down`)
  logs/            # Runner and web log files
  logs/postgres/   # The cluster's own log, one subdirectory per data directory
  workspaces/      # One subtree per workspace: shared files, community skills
  checkpoints/     # Shadow git store — snapshots taken before an agent writes
  snapshots/       # config.json and secrets.key saved with each copy of the database
  backups/         # what `nodal-agents backup` writes by default
```

To wipe everything and start fresh:

```bash
nodal-agents down
rm -rf ~/.nodalai
```

Your LLM provider keys, agents, jobs, and memory are all in `pg-data/`. The keys and tokens in it are encrypted with `secrets.key`, and the database opens only with the password in `config.json`: a copy of `pg-data/` is usable only together with those two files. To save an install, use `nodal-agents backup` (below): it takes the three together, in one file.

### If config.json or secrets.key is damaged

These files are replaced whole: a save that is interrupted leaves the previous version, never half of one. A file that exists but cannot be read (an edit that broke the JSON, a value Nodal does not accept) stops every command with an error that names the file and says what is wrong. Nothing is written over it, and Nodal never treats it as a first run. Fix the file, or copy `config.json.last-good` over `config.json`, then run the command again.

At start, Nodal also checks that `secrets.key` is the key this database was encrypted with, and refuses to start with another one.

## Start and stop

```bash
nodal-agents up      # start Postgres, runner (:3001), and dashboard (:3000)
nodal-agents down    # stop all services gracefully
```

`nodal-agents up` auto-cleans orphaned processes from a previous crashed session before starting. Postgres is always stopped gracefully (via `pg_ctl stop`) to avoid leaving shared-memory blocks that would block the next start.

Set `NODALAI_NO_BROWSER=1` to prevent the browser from opening automatically — useful on headless servers.

## Network modes

### Loopback (default)

Services bind to `127.0.0.1`. There is no password to type, but every caller still proves who it is with the install's secret, which only your account can read (`~/.nodalai/config.json`). This is the recommended mode for single-user local use.

- **The dashboard** opens through a link that `nodal-agents up` opens in your browser. The link works once, within 10 minutes, and leaves a cookie that keeps that browser in. Another browser or profile, or a bookmark opened before `up`, shows a page that says to run `nodal-agents open`: it opens a new link (`nodal-agents open --print` only prints it).
- **Your own scripts** that call the runner send `Authorization: Bearer <workerSecret>` (see [HTTP API](/docs/reference/api)).
- **Paired devices** keep their own key and are not affected.
- **After an update**, the first start opens the link as usual. A browser that was already on the dashboard before the update shows the page once: run `nodal-agents open`.

### LAN mode

Services bind to `0.0.0.0`, making the dashboard accessible to other devices on your network. LAN mode **requires sign-in** — the toggle enables email+password auth in the same write, so the config always stays bootable.

The recommended path is the dashboard: **Settings → Access → Network access → LAN**, then restart:

```bash
nodal-agents down && nodal-agents up
```

You can also run `nodal-agents init` and select **LAN**, or edit `~/.nodalai/config.json` directly (`"bind": "lan"`) and restart.

Who owns the account depends on the install:

- **Fresh install** — the first person to visit `http://<your-ip>:3000/login` signs up and becomes the admin. Sign-up closes after that.
- **Existing install** (it ran without a password before) — the login page detects that the owner exists but has no password yet, and shows **Create your account** instead of a dead sign-in. Set your email and password there: the account attaches to the existing owner, so your agents, settings and history stay exactly as they are. This is one-shot — once claimed, only sign-in remains.

### Auth modes

The runner supports three auth modes (`AUTH_MODE` in `apps/runner/src/env.ts`); all three are selectable from **Settings → Access → Sign-in**:

| Mode           | Behaviour                                                                                                                                                                           |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `local-trust`  | No password. Every caller proves it holds the install's secret: the dashboard through a launch link and its cookie, programs through `WORKER_SECRET`. Default for a loopback bind.  |
| `local-auth`   | Email + password sign-in. Default for a LAN bind. On a fresh install the first sign-up becomes the admin; on an existing install the owner claims the account (see LAN mode above). |
| `bearer-token` | The runner API requires a static `Authorization: Bearer <token>` header. Used for headless / programmatic access.                                                                   |

When you do not set a mode explicitly, it is derived from `bind`: `loopback` → `local-trust`, `lan` → `local-auth`.

### Auth override

You can enable email+password auth on a loopback install without switching to full LAN mode. The `config.json` schema (`apps/cli/src/lib/config.ts`) is:

```json
{
  "bind": "loopback",
  "auth": { "mode": "local-auth" }
}
```

`bind` is `"loopback"` or `"lan"`; `auth.mode` is `"local-auth"` (the override the wizard writes via Settings). Restart for the change to take effect. The dashboard then shows a login page at `/login`.

### Bearer-token mode

<Callout type="warn">
  Bearer-token mode is **not yet supported end-to-end**. The runner API honors `Authorization:
  Bearer …`, but the dashboard's bearer-token auth provider is still a scaffold that would fall back
  to no-auth — so enabling it would leave the web UI unprotected. To avoid that silent downgrade,
  `nodal-agents up` now **refuses to start** if `bearerToken` is present in `config.json`, with a
  clear error. Do not set `bearerToken` until this mode ships. For authenticated access today, use
  `auth.mode: "local-auth"` (email+password) above.
</Callout>

## Update

```bash
nodal-agents update
```

This command:

1. Fetches the latest version from the npm registry.
2. Installs it only when it is **newer** than the installed version. The same version, or an older one (a registry mirror that lags behind, or a pre-release you installed yourself), changes nothing and says so.
3. Otherwise, stops the running stack (`nodal-agents down`), installs exactly that version globally, and restarts the stack in the background.

The update itself does not touch `~/.nodalai/pg-data/`. The **next start** of the new version migrates the database to its schema, in place: make a backup first (`nodal-agents backup`, see [Backup and restore](#backup-and-restore)). Before it does, and only when there is a migration to apply to a database that holds data, `up` copies the database inside its own cluster and saves `config.json` and `secrets.key` beside the copy (in `~/.nodalai/snapshots/`). If that copy cannot be made (another program connected to the database, not enough free disk: the message gives the size of the copy and the free space), nothing is migrated and `up` stops. A copy takes about the size of the database on disk; the last two are kept (`"snapshots": { "keep": N }` in `config.json`).

### Going back after an update

A program older than its database refuses to start on it, and says which version migrated it. To go back:

```bash
nodal-agents down
nodal-agents rollback                 # lists the copies, newest first
nodal-agents rollback <copy-name>     # swaps one back in
npm install -g nodal-agents@<version> # the version that last opened it, named by the command
nodal-agents up
```

The swap keeps the database it replaces as a copy of its own; nothing is dropped. The master key travels with its database both ways. `config.json` is not changed (its database password and ports are the cluster's); the one saved with the copy stays in its folder under `snapshots/`. These copies live in the same cluster, on the same disk: they undo a faulty migration, not a lost disk. For that, make a backup.

## Backup and restore

```bash
nodal-agents backup                      # into ~/.nodalai/backups/
nodal-agents backup --to /mnt/usb --passphrase --keep 5
nodal-agents down
nodal-agents restore ~/.nodalai/backups/nodal-backup-20261128T090000000Z.nodalbak
nodal-agents up
```

**What a backup holds.** Every table of the database, the schema it belongs to, the master key (`secrets.key`), `config.json`, and with `--with-workspaces` the `workspaces/` folder: everything an install needs to live again. The folders you gave agents elsewhere on disk are your own files and are not in it; save them as you save the rest of your files.

**It is verified when it is made.** The file is read back and compared with the database, table by table, before the command says it is done; an interrupted backup leaves no file with a backup's name. It works while Nodal runs.

**It holds the master key.** Anyone who has the file can read every stored credential. Keep it where only you can read it, or use `--passphrase` (the passphrase cannot be recovered). The default folder is on the same disk as the install and `reset` deletes it: copy backups to another disk or machine.

**Restore keeps what it replaces.** The database a restore replaces becomes a copy that `nodal-agents rollback` can swap back. A backup from an older version is migrated by the installed one; a backup from a newer version is refused until you install that version.

### Moving to another machine

1. On the old machine: `nodal-agents backup --with-workspaces`, and copy the file across.
2. On the new one: `npm install -g nodal-agents`, then `nodal-agents restore <file>`. On a machine with no install, it creates one first. The settings of the backup come back; the ports and the database password stay this machine's own.
3. `nodal-agents up`. The restore lists the folders given to agents that do not exist on this machine.

The same path moves an install to a new major version of the embedded Postgres: a backup does not depend on the server's version, so it restores into a new, empty cluster.

To update without auto-restarting:

```bash
nodal-agents update --no-restart
# then manually:
nodal-agents up
```

If the npm registry is unreachable, the command exits with a clear message and a manual fallback:

```bash
npm install -g nodal-agents@latest && nodal-agents up
```

## Headless / server install

For a server with no interactive TTY, use the non-interactive init flag before starting:

```bash
nodal-agents init --non-interactive
nodal-agents up
```

The non-interactive init writes sensible defaults: LAN bind, `local-auth` mode, no LLM preset (finish LLM config in the dashboard after first login).

## Logs

Logs are written to `~/.nodalai/logs/`. Use the **Logs** page in the dashboard or the CLI:

```bash
nodal-agents logs
```

## Troubleshooting

**Port already in use** — `nodal-agents up` rotates to a free port automatically. Check the startup output for the resolved URL.

**Orphaned Postgres on Windows** — if `nodal-agents down` was skipped and you see a "pre-existing shared memory block" error, run:

```bash
nodal-agents down
```

If that fails, the startup output includes the exact `Stop-Process` or `kill` command to clear the orphan.

**Cannot reach npm registry during update** — run the manual fallback shown in the update output. No data is lost.
